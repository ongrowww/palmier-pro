## Findings considered and rejected

- Driving `codex exec --json` once per user message was rejected because it
  cannot provide a durable in-app thread, first-class approval handling, or a
  reliable lifecycle for cancellation and concurrent projects.
- Connecting the embedded Codex process back to Palmier over its HTTP MCP
  endpoint was rejected because Codex app-server dynamic tools can invoke the
  existing in-process `ToolExecutor` directly. The HTTP loop would introduce a
  second project context and duplicate session routing.
- Reimplementing Palmier tools specifically for Codex was rejected because
  `ToolDefinitions.inAppAgent` and `ToolExecutor` are already the authoritative
  schema and execution layers.
